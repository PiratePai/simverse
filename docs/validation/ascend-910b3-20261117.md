更新：2026-11-17。原采集提交 `6a16fbed8e6dc0982ed9abdea0ea1df6c006e429`。
本轮是在 Windows 上核对既有产物、采集源码并运行离线回归，**没有重新测量 NPU**。
原始 JSON/TXT/日志和采集脚本保留原字节；错误字段不得直接入账，以本报告及

## 1. 合入结论

证据可以作为待复核的局部观测归档，不能作为生产校准档。全部记录
`calibration_admission=not-admitted`；不加入 `PROFILE_SETS`，不改变 DEVICES、
V41_DEVICE_FAMILY、模型执行状态或部署排名。manifest 的 `source_kind=measured`
描述原采集来源，不表示通过 ProfileRecord 准入。文件哈希只证明归档一致性。

采集者报告环境：Ascend910B3、物理卡 6/7、CANN 9.1.0、driver 26.0.rc1、
torch 2.9.0+cpu、torch_npu 2.9.0.post9、Python 3.12.3、openEuler 22.03 aarch64。
torch/NPU 版本有局部日志；完整 CANN、拓扑快照、msprof 明细和 HCCL plog 未入库。
`diag_hccl.log` 没有 `transporttype[HCCS]`，故 HCCS 是采集者声明，尚不能由仓内证据独立验证。

## 2. 修正项及其依据

| 问题 | 审查后的结论 | 对应产物 / 下一步 |
|---|---|---|
| **P1：AllReduce busbw 少算 2 倍** | 采用 nccl-tests 的归一化定义时 `busbw = algbw × 2(P−1)/P`。P=2 的系数为 1；rank0、256 MiB 约 18.44 GB/s，原 9.22 错误。这里只重新计算派生指标，不把它当 HCCS 单向链路实测带宽 | 两份 `p1b_hccl_batch_rank*.json` 原字段保留；review.json 保存逐点修正值。参考官方 [AllReduceGetBw](https://github.com/NVIDIA/nccl-tests/blob/afd59abab774a6a4b492eb344bd0c845a0b7bb4d/src/all_reduce.cu) |
| **P1：ReduceScatter 形状不符合接口契约** | 脚本 input_list 每块 n 元素、output 为 n/P；list 接口要求每个输入块与 output 同形状。即使旧输出未报错，也不能据此认可 31.59 GB/s | 两份 HCCL 脚本该项隔离，重采须固定 total/send/recv 字节并验证结果。见 [PyTorch reduce_scatter](https://docs.pytorch.org/docs/2.9/distributed.html#torch.distributed.reduce_scatter) |
| **P1：graph 驻留归因错误** | `before−after=35,651,584 B`，而 `before−baseline` 同样为 35,651,584 B；即预热后 baseline 与 after 相等。可复算的净差是 0 B，不能据此声称 graph 池为零，也不能把全部预热差额算作 graph 额外驻留 | `p1a_runtime_pools.json`；重采 eager/预热/capture/replay/release 分阶段快照 |
| **P1：跨运行时间相减冒充 launch** | 18.74 µs（批内墙钟）和 7.08 µs（独立 msprof 的 GEMM task）不对应同一调用集合，不能相减得到 11.7 µs 的 launch。`mini_ops.py` 3 次预热+20 次调用，摘要 n=23，没有证明已剔除预热 | 撤销“六成是 launch”“长核吸收开销”及“融合后应小于 10 µs”等无证据结论；等待 correlation/stream/step 时间线 |
| **P1：预算阶段误读** | 原文把 torch 卡0的 `free_after_release=65,058,054,144` 写成 after_init。卡0真正 after_init 为 65,062,248,448 B；卡1释放后是 65,056,075,776 B，不是原文数值 | 两种 API、两阶段分栏如下；不自动授予 measured 部署预算 |
| **P1：MRoPE 成功结论不可重放** | 入库脚本从每个 section 的频率起点重新取值，原结果 `three_row_identity=false`，最大差 5.45075457596721。另一个 true/0 文件缺对应脚本；不能以该文件覆盖失败 | `p2_mrope_identity.json` 隔离，修复索引后用固定源码/独立 oracle 重采；当前参数 D=128/theta=1e6 也不是本仓 rotary=64/head=256/theta=1e7 |
| **P1：代理算子不等价** | moe_shared/routed 仅两次矩阵乘，缺独立 gate/up 的 SwiGLU；conv 输入长8、核4、无 padding，输出5，却按8计 FLOPs；RoPE 的 rotate_half 在计时窗口外；norm 为组合实现；稠密 SDPA 不等价稀疏/融合 attention | `p3_per_op_qwen.json` 的 analytic ratio 不可作为校准误差。测量 BF16 与原场景量化、实现和设备身份也未对齐 |
| **P2：ACL 返回码及内存归因不足** | ACL malloc 等返回码未检查，`ok=true` 只代表未抛 Python 异常；context 未传给 destroy_context。HCCL free 差包含首个张量/初始化；GEMM peak 差包含 allocator 对齐 | 原脚本仅作采集 provenance，不是推荐复跑入口；修正后另存新 run，不能覆盖原产物 |
| **P2：复现资料缺失** | 缺 p3 输入 `ops_qwen.csv`、`run_qwen.json` 及 revision/hash；缺 MRoPE identity 修正版；缺 msprof 聚合脚本、样本、命令；未保留多次 benchmark 结果 | 撤销“稳定锚点”“双卡 API 完全一致”及卡4比较，当前 TXT 只含一次观测 |

通信批内墙钟减少了每次同步的摊销，**没有扣除 host 下发和同步成本**。
各 collective 的 bytes_per_rank 不是统一的发送/接收总量，不能横向比较原 algbw
推断链路效率；连续原位 all_reduce(ones) 还会累积溢出，且脚本未验证输出正确性。
旧脚本保留用于审计，不应原样复跑生成新的可信证据。

## 3. 可以保留的局部事实

### 容量 API 快照（单位 B）

| 采样 | logical / 声明物理卡 | total | free_after_init | free_after_release |
|---|---|---:|---:|---:|
| torch | 0 / 6 | 65,452,113,920 | 65,062,248,448 | 65,058,054,144 |
| torch | 1 / 7 | 65,452,113,920 | 65,060,270,080 | 65,056,075,776 |
| ACL | 0 / 6 | 65,452,113,920 | 65,060,319,232 | 65,060,302,848 |
| ACL | 1 / 7 | 65,452,113,920 | 65,058,172,928 | 65,058,086,912 |

TORCH 逐次分配后释放；ACL 持有 1+4+8 GiB 累计分配；不能把两者当同一负载实验。
这些数是采集时空闲快照，不是常量规格，也不证明满容量可分配、无碎片或整模可行。
三个 allocator 样本 `reserved−requested=2,097,152 B`，但
`allocated−requested=512 B`，不是所有分配恒定多用 2 MiB 的定律。
GEMM 的 `peak−input−output=20,973,056 B` 是该脚本的额外峰值，尚未隔离纯 workspace。
HCCL 的 445,497,344 B 是初始化到首个 collective 的总 free 差，非纯通信器池。

### 数值与耗时观测

- SwiGLU 11 组与 MoE routing 5 组 FP32 组合实现的 oracle 对比记录可保留。
  它们验证这些测试输入，不证明官方 Ascend 融合核、模型级 forward 或 BF16 量化路径。
  MoE 当前 E=256 是缩小域；真实 V4.1 E/k、近阈值/平手/NaN 域仍须独立核验。
- RoPE 的 NPU FP32 与 CPU FP32 最大绝对差 4.76837158203125e−7 可保留为
  通用 fixture 观测。所谓 FP64 oracle 已共用 FP32 inv_freq，只是提升精度后运算，
  不是从参数全程 FP64 的独立 oracle；不能归因成纯三角函数误差或“2 ulp”。
- GEMM TXT 仅记录 BF16 8192³ 269.8 TFLOP/s、4096³ 129.9 TFLOP/s 等一次结果；
  copy 1217.5 GB/s 是读+写逻辑字节/墙钟，不是 HBM counter 实测或官方峰值。
- 23 条算子记录和 4 个 GEMM 形状的 msprof 摘要作为探索数据保留，缺少匹配原始
  样本/身份/映射，不能进训练、留出或生产 profile。

## 4. 后续实施与复现

权威排期见 [昇腾优先、少卡验证与 profiling 计划](../ascend-validation-plan.md)。
先修采集协议与 forward 路径，再采新 run；不通过修改历史数值伪装重测。
旧 scripts 中的绝对路径、ACL 返回码、通信形状、MRoPE 索引及 p3 代理问题均已登记。
复采输出到独立目录，提交完整输入、命令、环境、原始样本及 SHA256 后才能重新审查。

本轮检查入口：`py -3.12 -m pytest tests/test_ascend_evidence_r28.py -q`。
哈希/派生数值回归覆盖两 rank AllReduce 修正、graph 阶段差、预算阶段、MRoPE 冲突及
未准入状态；全量验证结果由 IMPLEMENTATION_STATUS 记录。没有硬件时这些检查只能
证明归档和审查结论自洽，不会解除 G-D7/R02b/R17/R18 或 G-C13/G-C16/G-C18。
